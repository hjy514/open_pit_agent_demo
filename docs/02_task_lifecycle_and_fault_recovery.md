# 里程碑 02：任务闭环与安全隔离故障恢复

日期：2026-08-01

## 1. 本阶段目标

上一里程碑已证明第三方程序能够发现三辆车、分配任务、下发目标并触发故障重调度。本阶段继续补齐“任务是否真正完成”和“抢占后原任务是否恢复”：

1. 车辆进入明确的距离容差后才算任务完成；
2. 任务长时间未完成时进入超时终态；
3. 高优先级任务可以抢占低优先级任务；
4. 高优先级任务完成后，原任务自动恢复；
5. 所有任务完成后，测试自动提前结束；
6. 每个状态变化写入可审计事件和汇总文件。

这些能力与地图无关。迁移到露天矿后，任务可从“到达 Town03 出生点”替换为“到达边坡复核区、救援点或封控点”，生命周期和证据结构保持不变。

## 2. 为什么拆成两个场景

### 2.1 正常闭环

`configs/town03.json` 使用三条相互独立的短路线，验证三辆车分别执行任务并完成。

### 2.2 安全隔离故障接管

`configs/town03_fault_recovery.json` 使用同一作业走廊，验证：

- 应急车执行最高优先级任务；
- 第 80 tick 注入执行能力故障；
- 故障车按配置横向隔离并停止；
- 巡检车02抢占最高优先级任务；
- 完成抢占任务后恢复原巡检任务。

该场景只代表“安全隔离后的执行能力故障”。道路中央抛锚会形成动态障碍，需要道路封控、绕行和路权协同，不能由本轮结果代替。

## 3. 完成判定的修正

初版同时接受 `BasicAgent.done()` 和距离容差。现场检查发现 CARLA 规划器可在距目标约 7–8 米时报告路线结束，即使配置容差是 3 米，造成验收口径不一致。

最终规则改为：

- 只按显式欧氏距离判断完成；
- Town03 功能演示容差明确配置为 8 米；
- 规划器报告结束但距离不合格时不得完成；
- 超过 `task_timeout_ticks` 后记录为 `timed_out`；
- 矿山阶段根据装备尺寸、制动距离和任务类型重新标定，不继承 Town03 的 8 米参数。

## 4. 路线校准

`scripts/inspect_map_routes.py` 现在同时输出：

- 全局道路路径长度；
- 车辆与目标的直线距离；
- 全局路线最后一个 waypoint 与请求目标的终点误差；
- 多辆指定车辆共同可达的候选目标。

这能区分“几何上很近”“道路拓扑可达”和“路线终点满足验收容差”。矿山地图导入后的第一项工作应是运行该工具检查路网连通性。

证据目录：

```text

```

结果：

| 指标 | 结果 |
|---|---:|
| 汇总状态 | PASS |
| 完成率 | 100%（3/3） |
| 故障注入 tick | 80 |
| 自动结束 tick | 899 |
| 高优先级任务接管完成 tick | 648 |
| 原任务恢复完成 tick | 898 |
| 三项完成距离 | 7.907 / 7.927 / 7.927 m |
| 超时任务 | 0 |

关键事件链：

1. `emergency_vehicle_01` 首次执行优先级 100 的 2 号任务；
2. 第 80 tick 进入 `safe_pull_over_then_disable`；
3. `inspection_vehicle_02` 的优先级 50 任务被抢占；
4. 2 号任务由巡检车02第二次执行并完成；
5. 巡检车02自动恢复 3 号任务并完成；
6. 故障车最终 `available=false`、`health=fault`、速度为 0。

安全隔离证据：

- 故障前位置约 `(-6.449, -42.143)`；
- 计算的安全停车目标约 `(-18.441, -42.571)`；
- 仿真结束实际位置约 `(-18.442, -42.543)`；
- 水平位置误差约 0.03 米。

故障场景使用 12 米横向隔离，因为 CARLA 0.9.10 BasicAgent 的车辆避障阈值为 10 米。该数值是 Town03 控制器测试参数，不是矿山规范参数。

## 7. 自动测试

当前 8 项测试全部通过：

1. Town03 配置和三类装备能力；
2. 初始调度分配给三辆不同车辆；
3. 故障任务释放和重新分配；
4. 控制器释放不销毁 CARLA 车辆；
5. 高优先级任务抢占；
6. 完成后启动队列中的下一任务；
7. 规划器结束但未进入距离容差时不得完成；
8. 安全隔离、手刹、物理冻结和事件字段。

## 8. 当前能力边界

已证明：

- 三辆普通车的能力约束调度；
- 真实 CARLA 状态读取和目标导航；
- 显式到达验收、任务超时结构和自动终止；
- 安全隔离故障后的任务接管；
- 高优先级抢占和原任务恢复；
- JSONL 事件与 JSON 汇总证据。

尚未证明：

- 露天矿地图、矿用车辆和重载工况；
- 道路中央抛锚后的动态避障、封控和绕行；
- 边坡多源监测、风险等级和预警准确性；
- 风险事件自动生成复核/救援/封控任务；
- 应急工单完整状态机；
- 同步仿真下的严格响应时间；
- 长时间稳定性、通信延迟和服务重启恢复；
- 大模型 Agent 或 MFS-LLM 的决策效果。

## 9. 下一里程碑

下一步建议接入“边坡风险事件到任务”的最小闭环：

1. 定义固定监测站和移动巡检观测数据；
2. 使用明确标注的合成数据构造正常、缓慢变形、加速变形和临滑阶段；
3. 建立透明可解释的蓝、黄、橙、红规则基线；
4. 橙色及以上风险自动生成高优先级复核任务；
5. 复用本里程碑的抢占、到达、完成和证据链；
6. 输出风险触发原因、响应 tick、任务变化和完成结果。

这样下一阶段仍可在 Town03 普通车辆上验证软件闭环，之后仅把风险区坐标、传感器数据源和车辆资产替换为露天矿版本。
