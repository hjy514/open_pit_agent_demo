# 露天矿统一场景系统设计

## 1. 文档定位与实现边界

本文档记录统一场景框架的设计、当前实现和真实性边界，避免把离线逻辑验证描述成CARLA物理验证。

- **统一框架（当前可运行）**：S01–S09 已进入统一目录和 `run_scenario.sh` 入口；S01–S07/S09 共享受约束的Episode生成、结构化事件、CARLA执行桥和数据契约，S08由固定三车Golden Demo兼容执行器承载。
- **比赛核心范围**：界面保留S01、S02、S04、S09与S08；其余场景作为扩展能力保留，不作为比赛现场逐一验收目标。
- 当前事件参数和风险数据属于工程约束下的合成仿真输入，尚未使用真实矿山生产数据完成统计标定，统一标记为 `ENGINEERING_BOUNDED_SYNTHETIC` 或 `NOT_CALIBRATED_WITH_REAL_MINE_DATA`。
- V1 继续作为 Rule-based Baseline、回归测试和比赛演示兼容层，不因 V2 建设被删除。

## 2. 核心原则

场景不等于一段写死的演示脚本，也不等于随机出生点。统一定义为：

```text
ConcreteEpisode = ConstrainedSampler(
    FunctionalScenario,
    LogicalScenario,
    MapResources,
    FleetProfile,
    Seed
)
```

场景系统分为三个层级：

1. **Functional Scenario**：说明发生什么、为什么发生、涉及哪些业务对象。
2. **Logical Scenario**：定义参数范围、概率/权重、依赖关系、硬约束和验收条件。
3. **Concrete Episode**：一次运行使用的不可变参数实例；包含确定 Seed，可以完整复现。

同一场景版本、地图资源版本、车辆规模、策略版本和 Seed 必须生成相同 Episode。场景运行中的实际反馈不回写静态 `map_resources.db`，而写入运行数据库 `openpit.db` 和本轮运行证据。

## 3. V2 统一生产底座

S01–S09 不再各自构造一套独立任务故事，而是共享下面的生产运行模型：

```text
车辆待命
  → 前往装载点
  → 装载点排队
  → 装载服务
  → 重载运输
  → 卸载点排队
  → 卸载服务
  → 空载返程
  → 接收下一循环任务
```

辅助车辆可以使用同一任务状态机的专业任务类型，例如道路巡检、边坡复核、应急保障和设备维护，但不得伪装成运输生产任务。

### 3.1 生产实体

| 实体 | 必需状态或属性 | 数据来源 |
|---|---|---|
| Vehicle | 角色、位置、载荷、健康、当前任务、速度、可用性 | 配置 + CARLA反馈 |
| HaulTask | 装载点、卸载点、优先级、载荷、截止时间、状态链 | Episode |
| Loader | 服务能力、队列、运行/故障状态 | Episode + RuntimeState |
| DumpPoint | 容量、队列、开放状态 | Episode + RuntimeState |
| Road/Edge | 长度、拓扑、状态、容量、风险、占用 | MapResources + RuntimeState |
| Environment | 降雨、能见度、路面能力等 | Episode + RuntimeState |
| Monitoring | 固定站、移动监测、数据质量 | RuntimeState |
| Risk | 等级、概率、区域、原因、道路影响 | Risk Engine |

当前没有可信装卸时间、产量和能耗数据时，字段保留但必须使用 `NOT_AVAILABLE` 或 `SURROGATE_ONLY`，不得虚构为真实测量值。

### 3.2 唯一状态源

场景、调度、风险、路径、CARLA 和 UI 统一围绕 `WorldState` 协作：

```text
ScenarioManager
      ↓
WorldState ← CARLA Feedback
      ↓
Risk Engine
      ↓
Decision Policy → Safety Shield → Route Planner → Execution
      ↓                                      ↑
Database / Events / Decisions / Experience Dataset
```

UI 只选择场景和发送控制命令，不在界面代码中复制调度、风险或事件逻辑。

## 4. ConcreteEpisode V2 统一格式

V2 的每次运行先生成并固化一个 Episode，然后才能生成车辆或进入 CARLA：

```json
{
  "schema_version": "openpit.concrete-episode.v2",
  "scenario_family": "s04",
  "scenario_version": "2.0",
  "episode_id": "s04-seed-202601",
  "seed": 202601,
  "complexity_level": "medium",
  "data_origin": "ENGINEERING_BOUNDED_SYNTHETIC",
  "calibration_status": "NOT_CALIBRATED_WITH_REAL_MINE_DATA",
  "map_context": {
    "map_id": "0325_5",
    "resource_version": "1.0-draft"
  },
  "fleet": [],
  "production_resources": {
    "loaders": [],
    "dump_points": [],
    "service_areas": []
  },
  "initial_tasks": [],
  "randomized_parameters": {},
  "parameter_provenance": {},
  "event_plan": [],
  "runtime_triggers": [],
  "hard_constraints": [],
  "admission_results": [],
  "success_criteria": [],
  "termination_criteria": []
}
```

Episode 是本轮实验输入，运行过程中不得被无记录地修改。实际事件时刻、车辆状态、决策和结果进入 RuntimeState、事件日志和数据库。

## 5. 随机性模型

### 5.1 随机对象

随机性分为六类，不能只随机车辆出生点和目标点：

| 类别 | 可变内容 |
|---|---|
| 生产需求 | 任务到达、任务优先级、装卸需求、任务积压 |
| 车队状态 | 车辆数、角色比例、初始任务、健康状态、可用性 |
| 空间关系 | 合法起点、作业点、路线、事件影响区 |
| 资源能力 | 装载点/卸载点容量、服务时间、道路通行能力 |
| 事件过程 | 类型、对象、强度、发生条件、持续时间、恢复条件 |
| 信息质量 | 监测噪声、延迟、缺测和置信度（有明确模型后启用） |

### 5.2 分布与来源

没有真实数据时，默认使用以下方法：

- 有上下限的工程范围；
- 带权离散集合；
- 多参数联合取值集合；
- 由条件规则表达的相关变量；
- 固定边界案例和回归案例。

不得因为方便就假定所有变量服从正态分布。每个随机字段必须保存 `source`、`distribution`、`range`、`unit` 和 `calibration_status`。获得真实数据后，才允许将工程范围替换为经验直方图、联合分布或拟合模型。

### 5.3 参数依赖

参数之间的因果关系必须显式表达。例如：

```text
heavy_rain
  → road_capacity下降
  → target_speed下降
  → travel_time上升
  → congestion_probability上升
  → task_delay上升
```

禁止生成语义冲突组合，例如道路已经关闭但路线仍使用该 Edge、故障车辆仍被作为可用候选、爆破尚未清场却进入执行阶段。

### 5.4 复杂度

复杂度不是简单增加事件数量，而由以下维度共同决定：

- 车队和任务规模；
- 同时活跃的作业资源数；
- 受影响车辆与道路比例；
- 候选方案和可替代路线数量；
- 队列、道路共享和任务依赖；
- 信息完整程度；
- 单事件或有因果顺序的复合事件。

`simple / medium / complex` 必须映射为明确参数范围，并随 Episode 保存，不能只作为展示标签。

## 6. 统一生成与准入流程

```text
读取Functional Scenario
→ 读取Logical Scenario参数空间
→ 使用Seed采样候选参数
→ 绑定地图和生产资源
→ 生成车队与生产任务
→ 生成事件计划和状态触发器
→ 业务因果检查
→ 地图/路线/冲突检查
→ 安全与可恢复性检查
→ 形成不可变ConcreteEpisode
→ 进入结构化仿真或CARLA
```

准入失败必须返回明确原因并保留采样证据，不得暗中减少车辆数量、替换事件语义或降低安全条件。统一失败类别包括：

- `INSUFFICIENT_VALID_RESOURCES`
- `NO_REACHABLE_PRODUCTION_CYCLE`
- `RESOURCE_CONFLICT`
- `EVENT_HAS_NO_OPERATIONAL_IMPACT`
- `NO_SAFE_RESPONSE_AVAILABLE`
- `DEPENDENCY_CONSTRAINT_VIOLATION`
- `INSUFFICIENT_RECOVERY_PATH`

结构化模式可以使用 P5 路线事实；CARLA 物理执行优先使用 P6 事实，使用 P5 候选时必须标记 `PENDING_CARLA_VALIDATION`。任何一种都不能自动升级为多车会车或碰撞安全证明。

## 7. S01–S09 功能场景与 V2 验收矩阵

以下表格是目标验收规则，不表示当前 V1 已全部实现。

| 场景 | 生产前置 | 合理触发与影响 | 调度/控制行为 | 恢复与完成标准 |
|---|---|---|---|---|
| S01 正常生产 | 多车进入完整生产循环 | 无突发事件；允许正常队列波动 | 周期性分配运输、巡检和保障任务 | 指定生产周期完成；无非法动作；全过程可追溯 |
| S02 车辆故障 | 被选车辆正在执行有效任务 | 根据健康状态或参数化故障条件触发；仅影响故障车及关联任务 | 故障车安全停车、任务释放、合法候选接管；其他车辆继续 | 接管任务和未受影响任务完成；记录恢复时间与切换代价 |
| S03 设备故障 | 装载设备存在服务队列 | 设备运行状态转为故障，服务能力降为零或受限 | 停止向故障点派新任务，排队车辆等待或转移至可用设备 | 设备恢复或任务转移完成；生产队列重新稳定 |
| S04 爆破管控 | 爆破前多车正常生产 | 计划预告→停止新任务进入→清场确认→封控 | 区内车辆撤离；受影响车辆绕行或等待；未受影响车辆继续 | 爆破窗口结束、安全复核、道路分阶段开放、生产恢复 |
| S05 极端天气 | 正常道路与生产负载存在 | 天气强度改变道路能力、速度和风险，不只是改变画面 | 安全限速、任务延迟评估、必要时改道或暂停高风险任务 | 天气缓解且道路评估通过；逐步恢复速度和任务 |
| S06 拥堵冲突 | 多车路线共享真实道路段 | 由道路占用、队列或服务瓶颈形成，不直接写死“拥堵” | 路权/时距控制、任务排序、可行时绕行 | 队列消散或低于阈值；所有车辆无碰撞通过 |
| S07 道路中断 | 至少一条活跃任务使用目标道路 | 道路状态变化必须影响真实任务路线 | 从可行图移除关闭 Edge；受影响任务重规划或安全等待 | 禁止进入关闭道路；替代路线或恢复后原路线完成 |
| S08 边坡失稳 | 正常生产并持续产生监测数据 | 监测量随时间演化，经 Risk Engine 达到分级阈值 | 复核、风险提示、受影响车辆停车/撤离/任务接管 | 风险处置、接管任务完成、复核和工单形成闭环 |
| S09 复合扰动 | 正常生产且资源足以产生有效影响 | 两个以上事件具有明确先后或因果关系，不能简单同时播放 | 每次事件后基于最新 WorldState 重新决策 | 各事件均被处置；无互相覆盖的非法控制；生产最终恢复 |

### 7.1 全场景共同验收条件

每个 ConcreteEpisode 至少满足：

1. 事件前确实存在可观察的多车正常生产阶段；
2. 事件由计划条件或运行状态触发，并记录触发证据；
3. 事件影响对象与车辆位置、任务或路线存在真实关联；
4. 未受影响车辆继续原任务；
5. 决策发生在事件之后，不能提前把最终方案写成已执行；
6. Safety Shield 拒绝故障车、关闭道路、能力不匹配等非法动作；
7. 恢复条件满足后才恢复车辆和道路；
8. 场景以业务目标完成或明确安全失败结束，不以任意短时限冒充完成；
9. 同 Seed 可复现，不同 Seed 在合法参数空间内产生有意义变化；
10. Episode、状态、事件、决策、执行反馈和指标可由数据库关联还原。

## 8. 生命周期与调度中心控制

运行生命周期为：

```text
PREPARING → RUNNING → PAUSED ↔ RUNNING
                     ↓
              EVENT_ACTIVE → RECOVERING
                     ↓
          COMPLETED / FAILED / TERMINATED
```

调度中心通过统一接口工作：

| 接口 | 用途 |
|---|---|
| `GET /scenario/catalog` | 读取场景、车辆规模、模式和策略 |
| `POST /scenario/control/start` | 创建并启动一轮场景 |
| `POST /scenario/control/pause` | 安全制动车辆并冻结场景进度 |
| `POST /scenario/control/resume` | 保持同一运行上下文继续 |
| `POST /scenario/control/terminate` | 明确结束本轮运行 |
| `GET /scenario/control/status` | 读取状态、结果、运行 ID 和数据库位置 |

当前暂停/继续已接入 S01–S07/S09 的统一执行进程。S08 仍使用 Golden 兼容执行器，暂不宣称支持保留现场暂停。

## 9. 数据记录边界

- `map_resources.db`：保存出生点、道路拓扑、路线长度、可达性和验证等级等静态地图事实。
- `openpit.db`：保存 Episode、车辆、任务、运行事件、风险、决策、路线计划、执行反馈、指标和模型版本。
- `data/logs/`：保存系统和诊断日志。
- `data/datasets/`：保存经过质量检查的训练转换数据，不直接把全部日志当训练集。
- `artifacts/runs/`：保存每轮可审计证据和报告。

场景中的交通、天气、风险、道路临时关闭和车辆故障属于 RuntimeState，不得写回静态地图资源库。

## 10. 从 V1 到 V2 的渐进迁移

为避免再次形成大量场景专用脚本，V2 优先升级现有公共模块：

| 现有模块 | V2 职责 | 迁移方式 |
|---|---|---|
| `scenario/models.py` | LogicalScenario、ConcreteEpisode、生产资源与统一状态契约 | 原地扩展并保留 V1 序列化兼容 |
| `scenario/generator.py` | 受约束采样、参数依赖、复杂度和准入结果 | 升级为所有场景唯一生成入口 |
| `scenario/runner.py` | 生产状态机、事件触发、完成判定 | 逐步替换预先计算的事件结果 |
| `scenario/carla_execution.py` | 执行 ConcreteEpisode 并反馈 WorldState | 不承担随机规则和业务决策 |
| `scenario/s02...s09_runner.py` | 当前 V1 兼容行为 | 保留回归；逻辑逐步收敛为事件处理函数 |
| `configs/scenario_catalog.json` | 功能场景目录 | 不存放具体 Episode |
| 各场景配置 | 逻辑参数空间和来源 | 逐步升级，不复制执行代码 |

实施顺序：

1. 冻结当前 V1 回归结果；
2. 在现有模型中增加 V2 Episode 与生产资源契约；
3. 在现有生成器中增加参数来源、依赖、复杂度和统一准入；
4. 先让 S01 跑通真实多车生产循环；
5. 将 S02–S09 的事件依次接入同一生产状态机；
6. 结构化模式验证逻辑和数据，CARLA 验证物理执行；
7. 使用固定 Seed 做 V1/V2 回归和策略 A/B 对比；
8. 获得真实矿山数据后再进行概率和参数标定。

## 11. 当前完成标准与后续边界

统一场景框架按以下标准维护：

- S01–S09 均能由同一 Episode 格式表达；
- 随机变量、依赖、来源和准入失败均有统一位置；
- 场景内容建立在生产循环上，而不是按 tick 播放孤立事件；
- 结构化模式和 CARLA 使用同一 ConcreteEpisode；
- 数据库能够保存生成输入、运行反馈和最终结果；
- 不需要为每个新需求继续创建新的独立 Runner 或版本脚本。

后续新增能力应继续扩展现有 `ConcreteEpisode`、生产资源模型和公共执行桥，不再为单个需求建立独立Runner或版本脚本；任何修改都必须保持S08 Golden Demo和比赛核心场景回归兼容。
