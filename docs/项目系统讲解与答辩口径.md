# OpenPit-Agent 露天矿智能调度与风险闭环系统讲解

## 1. 项目一句话定位

OpenPit-Agent 是一个以 **CARLA 自定义露天矿地图 `0325_5`** 为数字矿山验证环境，融合固定监测、移动装备监测、边坡风险研判、装备任务调度、人机协同确认、矿卡执行与运行数据留存的露天矿安全调度原型系统。

系统当前的核心特点不是“让一个黑盒模型直接开车”，而是：

```text
可解释规则决策 + CARLA高保真执行验证 + 人工确认 + 数据留存
```

它为后续引入风险预测模型、学习型调度策略和风险感知路径规划提供数据与验证底座。

### 2.1 CARLA 仿真层

CARLA 0.9.10 是项目的数字矿山执行层，负责：

- 加载自定义矿山地图 `0325_5`；
- 加载矿卡蓝图，例如 `vehicle.cat.cat`；
- 生成、销毁和读取车辆Actor；
- 提供车辆位置、速度、姿态、控制状态；
- 提供Spawn Point、Driving Lane、Waypoint 和道路拓扑；
- 通过 `BasicAgent` 执行底层跟踪、油门、制动和转向；
- 通过 `GlobalRoutePlannerDAO + GlobalRoutePlanner` 生成CARLA道路级路线；
- 输出全局与多车相机帧。

CARLA 的定位是 **高保真验证环境**。调度器决定“谁做什么”，CARLA负责验证“这辆车是否真的能在仿真矿山中完成动作”。

### 2.2 Agent 后端

后端位于 `src/open_pit_agent/`，入口为 `run_demo.py`，实际编排位于 `cli.py`。

它并不是一个单独的大模型，而是由多个可解释的职责模块组成：

| 模块 | 主要文件 | 实际职责 |
|---|---|---|
| 配置与数据模型 | `config.py`、`models.py` | 读取车辆、区域、任务、CARLA和场景配置；定义车辆、任务、位置、分派等对象 |
| 场景系统 | `scenario/`、`scenario_runtime.py` | 定义S01–S07、S09结构化场景和S08 CARLA Golden Demo，支持Seed与6/8车编组 |
| 监测系统 | `monitoring.py` | 固定监测站和移动设备观测、数据质量字段、采样批次 |
| 风险引擎 | `risk.py` | 对监测指标进行蓝黄橙红阈值研判，生成风险原因和风险动作 |
| 决策解释 | `decision_intelligence.py` | 形成候选车辆、推荐理由、风险处置建议、经验记录和验收报告 |
| 调度器 | `scheduler.py` | 能力筛选、距离/负荷综合评分、优先级任务、故障释放与重新分配 |
| 道路限制与工单 | `restrictions.py`、`work_order.py` | 管控风险道路、管理风险工单状态流转 |
| CARLA适配器 | `adapters/carla_adapter.py` | 将调度任务转换成CARLA车辆Actor、BasicAgent路线和控制命令 |
| API与运行状态 | `interfaces/api_server.py`、`runtime_state.py` | 向调度中心提供状态，接收人工命令并回执 |
| 证据与数据库 | `evidence.py`、`sqlite_store.py` | 保存运行日志、结构化业务记录、经验样本和验收结果 |
| 地图资源库 | `map_resources/` | 保存出生点、冲突、可达性、道路和候选路线等长期地图事实 |

### 2.3 PyQt6 调度中心

`open_pit_dispatch_app/` 是独立桌面客户端，不承担风险计算和调度算法。

它通过HTTP从后端读取状态，主要功能包括：

- 动态矿山态势地图；
- 车辆位置、任务、健康、通信、速度和轨迹展示；
- 任务区、监测站、风险区和规划路线展示；
- 实时事件流与闭环状态展示；
- 智能调度方案、候选车辆代价、硬约束和工单查看；
- 人工调度、暂停、恢复、紧急停车和方案确认；
- 全局与多车相机墙：保留一路全局画面，三个车辆画面可从当前运行矿卡中自由选择。

比赛界面的场景下拉框只保留 S01 正常生产、S02 车辆故障、
S04 爆破与临时管控、S09 复合道路/车辆扰动和 S08 边坡 Golden
Demo。完整 S01–S09 工程目录仍保留在后端和命令行，不在比赛主界面
造成干扰。从界面启动四个多车场景时，统一使用 0.8 展示速度系数，
并同步增加任务执行预算；这只改变 CARLA 的展示节奏，不改变随机 Seed、
调度决策、风险事件或数据库格式。S08 Golden Demo 的速度和摄像头配置保持不变。

地图组件默认每500毫秒调用API刷新，不在UI内部重新计算任务或风险。
CARLA执行期间同样每10 Tick（当前约0.5秒）向界面发布一次车辆位置，
但用于运行结果和数据集的完整遥测仍每100 Tick记录，避免为了界面动画
而将数据库与结果文件放大十倍。

## 3. 底层算法与决策逻辑

### 3.1 风险研判：透明阈值模型

当前边坡风险使用 `RuleBasedRiskEngine`，输入来自固定站和移动设备的合成演示监测数据。每个观测包含例如降雨、位移、裂缝、含水率、车辆巡检指标等字段。

风险等级按如下逻辑产生：

```text
若未达到黄色任何阈值 → 蓝色
若达到黄色阈值         → 黄色
若达到橙色阈值         → 橙色
若达到红色阈值         → 红色
```

当多个阈值同时满足时，采用最高风险等级，并记录触发理由，例如：

```text
位移=… ≥ 红色阈值
裂缝=… ≥ 红色阈值
```

因此每次风险判断都能回答三个问题：

1. 当前是什么等级；
2. 相比上一时刻是在上升、下降还是稳定；
3. 是哪些监测指标触发了该等级。

当前风险数据明确标记为 `synthetic_data=true`，用于仿真验证，不能表述为真实矿山生产数据。

### 3.2 调度决策：能力约束 + 综合代价评分

当前“AI调度决策”的核心是 `BaselineScheduler`，属于透明、可复现实规则策略，版本标识为：

```text
capability-distance-load-transparent-v1
```

它不是已经训练完成的LLM、PPO或深度强化学习模型。

调度过程分两步：

**第一步：硬约束筛选**

车辆只有同时满足以下条件才进入候选集：

- 车辆可用；
- 健康状态为`healthy`；
- 不在排除名单中；
- 车辆能力集合覆盖任务要求。

例如需要“相机+激光雷达”的边坡复核任务，普通运输车不能被选中。

**第二步：综合代价评分**

对每辆候选车辆计算：

```text
Score = Distance + Load × LoadPenalty − ExperienceBonus
```

其中：

- `Distance`：车辆当前位置到目标区域的欧氏距离；
- `Load`：该车正在执行或已分派的未完成任务数；
- `LoadPenalty`：默认1000米等价惩罚，避免同一辆车被反复分派；
- `ExperienceBonus`：从历史成功样本读取的有限偏好奖励，最大不超过2米等价分，不能覆盖安全约束。

分数越低越优。任务按“优先级降序、创建时间、任务ID”稳定排序，保证相同输入下结果可复现。

### 3.3 故障、抢占与任务接管

当车辆故障或边坡风险影响原任务时，系统不简单删除任务，而是执行：

```text
原任务执行中
→ 受影响车辆安全停止/标记异常
→ 未完成任务释放为pending
→ 保存原车辆ID和接管原因
→ 重新评估具备能力的候选车辆
→ 生成推荐车辆和候选评分
→ 人工确认
→ 新车辆接管并执行原任务目标
```

这对应演示中的“矿卡1受影响，附近合适矿卡接管其未完成任务；其他车辆继续原任务”。

### 3.4 路径与车辆执行：规划和控制分层

项目明确区分：

```text
上层规划：应该经由哪些路段/安全点到目标？
底层执行：CARLA中如何控制矿卡沿路线行驶？
```

当前正式Demo的底层执行采用CARLA `BasicAgent`：

```text
调度任务
→ 目标区域对应的Spawn Point
→ BasicAgent.set_destination / 导航腿
→ VehicleControl（油门、制动、转向）
→ CARLA物理引擎
→ 车辆状态和事件反馈
```

风险改道不是把路线画在界面上就结束，而是将安全Waypoint拆成多段真实导航腿：

```text
当前位置 → 安全点B1 → 安全点B2 → 最终任务点
```

每到一个中间点，适配器再启动下一段`BasicAgent`导航。

当前自定义矿图上层路网还处于建设阶段。P5使用CARLA `GlobalRoutePlanner`验证Spawn Point之间是否存在道路级路线；它只说明规划器能否生成路线，不等于矿卡已真实跑通、净空通过或多车无碰撞。

### 3.5 安全约束

安全逻辑不交给经验偏好或未来学习模型直接覆盖。当前已经具备的约束包括：

- 故障车辆不可继续接收任务；
- 能力不满足的车辆不可接收任务；
- 风险升级时生成复核、道路管控和应急任务；
- 道路限制可以取消风险区内不允许类型的任务；
- 红色风险下的任务接管需要人工确认；
- 待复核路线不进入自动派单。

后续可进一步独立为`Safety Shield`，作为任何学习策略的最终动作审查层。

## 4. 一次边坡失稳综合场景的完整流程

以当前边坡风险演示为例：

```text
1. 启动CARLA，加载0325_5和矿卡蓝图
2. 后端读取矿山配置、监测配置、边坡风险配置
3. 生成/发现配置中的矿卡，分配常规巡检或运输任务
4. 固定监测站和移动装备采集观测数据
5. 风险引擎输出蓝 → 黄 → 橙 → 红的评估与原因
6. 黄色：提高关注和复测建议
7. 橙色：生成融合复核任务，推荐有相机/激光雷达能力的车辆
8. 红色：受影响车辆安全停车，释放未完成任务
9. 调度器计算候选接管车辆，输出分数、理由和推荐方案
10. 调度中心显示方案，调度员确认或修改
11. 后端读取确认命令，新车辆接管原任务
12. CARLA BasicAgent按安全导航腿前往原任务目标
13. 车辆执行事件、工单状态和复核结果回传
14. 风险下降后解除限制，工单进入复核、关闭和反馈
15. 保存运行摘要、事件、任务、决策、监测和证据
```

这构成了实时执行闭环：

```text
感知 → 风险研判 → 决策 → 人工确认 → 调度 → CARLA执行 → 反馈 → 状态更新
```

下列是当前最稳定的“三车边坡风险综合Demo”启动方式。需要打开四个终端，每个进程都保持运行。当前本机启动脚本会自动识别`openpit-agent`、`openpit-ui`和CARLA 0.9.10，无需在日常演示时手动输入`export`。

P6会进一步对其中5条业务任务路线进行单矿卡真实行驶验证：

P6每次只生成一辆`vehicle.cat.cat`，记录到达、超时、卡死或终点偏差后销毁Actor。它仍不代表多车碰撞、会车或净空安全。

## 5. API、界面与CARLA如何调用

### 5.1 启动链路

典型运行顺序：

```text
CarlaUE4.sh
→ start_api.sh（FastAPI）
→ start_dispatch_app.sh（PyQt6）
→ start_slope_demo.sh 或 run_demo.py（后端场景）
```

`run_demo.py`调用`cli.main()`；在`carla-run`模式中，`run_carla()`创建调度器、风险引擎、工单管理器、限制注册器和`CarlaAdapter`，再进入按Tick推进的循环。

### 5.2 状态和命令双向链路

```text
CARLA运行进程
  └─ POST /runtime/sync
       └─ FastAPI RuntimeState
            └─ PyQt GET /state、/map_state、/monitoring、/events

PyQt人工操作
  └─ POST /commands 或 /manual_dispatch
       └─ RuntimeState命令队列
            └─ CARLA运行进程轮询 /commands/pending
                 └─ 执行、POST /commands/{id}/ack 回执
```

主要接口包括：

| 接口 | 用途 |
|---|---|
| `GET /vehicles` | 车辆实时状态 |
| `GET /map_state` | 地图道路、区域、车辆、轨迹、路线 |
| `GET /monitoring` | 固定/移动观测、风险、工单和闭环状态 |
| `GET /learning/status` | 有效CARLA运行、决策经验、正式/Shadow策略和下一阶段 |
| `GET /events` | 实时事件流 |
| `GET /camera/streams` | 多车相机流元数据 |
| `POST /runtime/sync` | 后端向API同步完整运行快照 |
| `POST /commands` | 人工调度、暂停、恢复、急停等命令入队 |
| `POST /commands/{id}/ack` | CARLA运行进程回执命令执行结果 |

## 6. 数据库、证据和地图资源库

项目有两类SQLite数据库，职责不能混淆。

### 6.1 `data/database/openpit.db`：运行业务数据库

它记录“某一次场景运行发生了什么”，包括：

- `scenario_runs`：一次运行基本信息、Seed、状态和摘要；
- `events`：事件时间线；
- `tasks`、`task_transitions`：任务及状态变化；
- `risk_assessments`：风险结果、原因和指标；
- `decisions`、`decision_candidates`：决策与候选车辆评分；
- `route_plans`：运行中的路线计划；
- `work_orders`：风险工单；
- `monitoring_batches`：监测批次；
- `metrics`、`artifacts`：指标和文件索引；
- `vehicle_master`、`run_vehicles`：车辆主数据和运行快照；
- `episode_tasks`、`episode_events`：场景具体实例。
- `training_runs`：候选模型的训练批次和报告路径；
- `policy_versions`：正式策略与Shadow候选策略的版本、权限和数据来源；
- `policy_evaluations`：离线留出集评估结果。

后三张表只记录低频模型治理事实，不存车辆高频遥测，也不改变
`map_resources.db`的静态地图资源职责。

### 6.2 `data/database/map_resources.db`：地图长期资源事实库

它记录“这张矿山地图本身有什么资源、什么经过验证”，不会被每次场景运行覆盖。

| 阶段 | 当前内容 | 当前结论边界 |
|---|---|---|
| P3 | 82个`VERIFIED_SPAWN`出生点 | 单辆矿卡可生成且基础Driving Lane检查通过 |
| P4 | 77个近距离候选点对；61对双车可同时Spawn、16对不通过 | 仅验证同时生成，不代表可同行或不碰撞 |
| P5 | 82个点的6642个有向点对已全部分类：2749个严格可达、1397个近终点、2496个终点偏差 | 仅验证CARLA规划器路线，不代表真实行驶成功 |
| 路网候选 | 2749个严格可达点对已映射为CARLA拓扑边序列；其2599个通过P5/拓扑长度一致性门槛，150个标记为长度不一致 | 状态为`TOPOLOGY_DERIVED_UNVERIFIED`的记录可用于离线道路影响分析；`TOPOLOGY_LENGTH_MISMATCH`不进入S07；两者都不代表物理通行安全 |

当前P5.1代码将路线分为：

```text
PLANNER_REACHABLE        终点误差≤5m，可作为后续候选
PLANNER_NEAR_ENDPOINT    5～15m，只能待单车复核
PLANNER_ENDPOINT_MISMATCH >15m，排除
PLANNER_UNREACHABLE      空路线
PLANNER_ERROR            接口异常，下一次重试
```

当路网拓扑或P5可达结果更新后，执行
`./map_resources.sh build-route-candidates`重建关联。该过程不连接CARLA，
只替换同一派生来源的候选，不删除人工或实车采集路线。

### 6.3 文件证据和训练基础

每次运行的`artifacts/runs/<run_id>/`保存JSON、JSONL、截图、监测观测、事件、任务、决策、工单、验收报告等可追溯证据。

`experience_dataset.jsonl`是原三车Demo的兼容经验文件，历史成功样本只能产生很小的`ExperienceBonus`，不能越过能力、故障和安全约束。

统一多场景入口会把S01–S07及S09的决策记录导出到
`data/datasets/openpit-structural-transition-v1/<dataset_id>/`，七个场景共用
`state/action/result/next_state/done`格式，并保留Scenario、Seed、车辆数、
地图资源版本、候选评分、执行策略和数据库闭环验收结果。
它目前仍是“决策到结构化终态”的BC准备数据，不是CARLA逐时步轨迹。
`structural-terminal-reward-v1`使用可追溯的任务完成、数据库闭环证据、故障/封路处置、
换车与绕行代价生成结构化终态Reward，并保留每个分项的来源和可用性。
这些权重是尚未经敏感性分析的初始工程权重，不是论文已证明的最优权重；
真实能耗、碰撞和CARLA物理性能仍为`NOT_AVAILABLE`，不可直接宣称已完成PPO训练。

CARLA统一执行桥接还会在初始派单、场景事件响应和运行中任务恢复时，
记录`openpit.decision-experience.v1`决策边界样本。每条包含决策Tick、
决策前状态、实际动作、安全审核、关联路线和动作后状态，同时写入
`artifacts/runs/<run_id>/decision_experiences.jsonl`和`openpit.db.events`。
离线导出器将当前状态连接到下一决策或场景终局，形成决策级
`(s,a,r,s',done)`。`carla-decision-experience-reward-v1`只使用任务完成增量、
终局成功、决策区间耗时、任务失败、换车与显式安全拒绝等已记录事实。
缺失分项保持`NOT_AVAILABLE`并排除出加权均值，不伪造能耗或产量。
导出命令为：

```bash
./run_scenario.sh --export-decision-dataset \
  --dataset-version carla-decision-reward-v1 \
  --scenario s02
```

该数据集当前只授权离线分析和BC准备，`eligible_for_ppo_training=false`，
不会自动训练、不会在下一次运行时自动替换正式策略。

每个批次的`manifest.json`还包含数据质量报告：除样本数和Reward外，
还显式展示场景/Seed覆盖、动作类型、车辆选择、故障车和封路边分布，
并对重复经验ID、关键字段缺失、场景缺失、数据库闭环证据和失败运行进行检查。
这使得“批量运行成功”和“数据足以用于后续学习”成为两个独立结论。

通过同一`run_scenario.py --aggregate-datasets`入口，可将通过质量检查且Reward版本一致的
批次聚合为固定Dataset Version。系统按Seed整组划分`train/validation/test`，
并对重复运行进行语义去重，因此同一随机场景不会同时出现在训练集与测试集。
每个划分还会检查场景与动作覆盖；覆盖不足时只标记警告，不复制或伪造样本。

当前已建立纯Python的`behavior-cloning-candidate-ranker-v1`。它以同一任务的合法候选车辆
为Softmax选择集，学习路线长度、归一化运输代价、负载、切换代价和多目标总代价。
硬约束失败的候选不进入模型，结果无效时必须回退到Heuristic Baseline。

首个110-Seed离线模型在多候选测试集上的Top-1为48.94%，均匀机会基线为47.52%。
故障重分配子集为100%，但正常全局分配的多候选子集只有45.45%。
原因是现有教师实际进行全局唯一分配，而当前Transition只包含单任务候选状态。
因此该模型只能作为Shadow试验模型，当前明确不提升、不接管正式Demo。

当前已接入受控的慢闭环：系统默认每累积20次核心场景有效
CARLA运行后提示进行一次策略更新检查，但不在场景运行过程中在线替换模型。
可通过统一入口查看门槛、核心场景覆盖、决策经验数和当前策略：

```bash
./run_scenario.sh --learning-status
```

当门槛达成且已准备不可变的结构化Dataset Version后，可手动生成候选策略：

```bash
./run_scenario.sh --prepare-policy-candidate \
  --dataset-version structural-bc-v1-110seeds-20260906 \
  --model-version bc-candidate-competition-v1 \
  --policy-scope candidate
```

该命令只执行“结构化教师数据训练→留出集离线评估→Shadow版本登记”。
CARLA决策经验用于触发更新检查和后续A/B验证，现有BC训练器不会假称用了
CARLA轨迹数据。候选策略始终是`shadow_only`，必须经人工审查和CARLA A/B后才能另行晋级。

随机地图S01现已支持通过统一入口选择实际结构化执行策略：默认
`--policy heuristic`继续执行`heuristic-route-load-global-unique-v0`；指定
`--policy multi-objective`时执行`multi-objective-cost-v1`和
`global-unique-multi-objective-v1`。系统使用相同Scenario和Seed保留两套分配，
输出选择变化、归一化总代价与路线总长，并把实际策略版本写入`openpit.db`。
这属于离线结构化A/B执行，尚未获得CARLA多车物理执行权限。S02故障接管也已
支持同一开关：初始分配保持V0，故障后的接管候选经过硬约束后由V1实际选择。
当前Heuristic V0和MultiObjective V1的实际执行都经过同一
`ClosedLoopCoordinator`和Safety Shield执行门，并以相同的
State、Action、Feedback、Next State格式写入`closed_loop_cycles`，
因此可以用同Scenario、同Seed进行可追溯对照。
统一入口可直接执行这种配对对照，无需分别运行和人工整理：

```bash
./run_scenario.sh \
  --scenario s01 \
  --compare-policies \
  --runs 10 \
  --vehicle-count 6 \
  --seed 202700
```

系统会对每个Seed分别实际执行Heuristic V0和MultiObjective V1，
并在`artifacts/batches/policy-ab-*/summary.json`输出配对通过率、
任务车辆选择变化、归一化代价变化、路线总长变化和Safety Shield
结果。如果两种策略结果一致，报告保留零改善结论，不人为放大差异。
当前S02除路线长度外的等待、延误和恢复时间仍不可用，因此V1可能合理退化成
与V0相同的最短路线选择。S07道路重规划仍执行原有确定性路网逻辑。

## 7. 多场景、多车辆和随机性的现状

当前已具备的开发基础：

- S01：六车正常任务分派Mock；
- S02：六车车辆故障、任务释放与重分派Mock；
- S03：装载设备故障后，将故障作业点作为硬约束排除，受影响运输任务切换到地图资源库中可达的替代作业点，其他任务保持不变；
- S04：在参数化爆破时间窗内锚定一条真实拓扑道路实施临时管控；原车有安全绕行时绕行，无绕行时等待解除，不执行无依据换车；
- S05：基于真实地图拓扑边的参数化极端降雨与道路能力下降；比较降速通行和安全绕行，天气输入为合成参数，ETA为工程估算而非CARLA实测；
- S06：从本轮真实拓扑路线中选择多车共享道路段，以容量1、参数化初始阻塞和安全车头时距生成排队放行计划；时间为路线长度与配置速度推算值，不是Traffic Manager或CARLA实测；
- S07：基于真实路网边的可复现6/8车道路中断；原车可绕行时保持原车，无安全绕行时才由合法候选车接管，未受影响任务保持不变；
- S09：在同一地图、车队和任务状态上先施加道路封闭，再施加车辆故障；故障任务只能由能力匹配、P5点对可用且避开封闭边的候选车接管；
- 批量闭环：通过`./run_scenario.sh --scenario all --mode structural --runs N`连续运行S01–S07及S09，每轮独立入库并生成批次指标。
- 自动验收：区分“程序运行成功”与“业务闭环证据通过”，检查任务终态、故障车排除、事件顺序、道路规避、决策和路线入库记录。
- 边坡风险Golden Demo：三辆矿卡的CARLA综合验证；
- P3/P4/P5：为未来多车随机场景建立地图资源事实。

需要如实说明：S01–S07及S09已具备统一CARLA执行代码和数据闭环，但不等价于所有Seed、路线和6/8车组合都已完成物理实跑。

项目对外只推荐一个场景命令`./run_scenario.sh`：`--mode structural`
执行批量数据闭环，`--mode carla`执行S01–S07/S09的6/8车事件控制，
`--scenario s08 --mode carla`继续复用三车边坡Golden Demo。例如：

```bash
./run_scenario.sh --scenario s02 --mode carla --vehicle-count 6 --seed 202601 --ticks 1000
```

从调度中心启动时，后端仍调用这一统一入口，但会同步CARLA实时状态并启用
DecisionPoint人工确认门：事件发生后先安全暂停，主界面只发出提醒；调度员进入决策中心审阅候选车辆、代价和硬约束。接受推荐方案时直接批准；人工改派时先下派所选车辆与任务，确认指令入队后再批准事件方案。驳回或超时不视为批准，场景以受控安全结果结束。该门是运行期安全控制。界面同时区分“实时执行闭环”和“学习数据闭环”；后者当前只积累状态、决策、代价和反馈，不代表在线学习或模型自动更新。

S09当前是“道路封闭+车辆故障”两事件V1，不能扩大表述为任意多事件组合。

后续的正确路径是：

```text
地图可用出生点
→ 排除P4冲突点对
→ 选择P5规划可达的任务点
→ 生成满足角色/能力约束的6～8车编组
→ 单车真实路线验证
→ 多车CARLA验证
→ 批量随机场景运行
→ 形成可训练经验数据集
```

随机性必须由Seed控制，并受地图资源约束；不能随机把矿卡放到未验证点，也不能随机分派到不可达任务点。

## 8. 当前能力边界与答辩表述

建议如实表述：

| 可以明确说已实现 | 不应夸大为已实现 |
|---|---|
| CARLA自定义露天矿地图和矿卡仿真 | 真实矿山生产数据闭环 |
| 三车边坡风险演示和任务接管闭环 | 全图多车真实无碰撞运行 |
| 固定站与移动装备的合成监测数据 | 已训练好的深度风险预测模型 |
| 可解释风险阈值与综合代价调度 | 已部署的大语言模型自主决策 |
| 人工确认、命令回执、工单流转 | 完整PPO/BC在线训练与策略提升 |
| SQLite运行数据与地图资源库 | 所有道路均完成重型矿卡净空验证 |

更准确的答辩用语是：

> 当前系统采用可解释规则策略作为安全基线，通过CARLA自定义矿山地图验证感知、风险研判、任务接管和人机协同闭环；同时持续沉淀地图资源、运行记录和经验样本，为后续风险模型、学习型调度策略与风险感知路径规划提供可复现实验数据。

## 9. 建议的汇报顺序

1. **问题背景**：露天矿边坡、极端天气和装备故障会使原计划失效。
2. **总体方案**：CARLA数字矿山 + Agent后端 + 调度中心 + 数据库。
3. **感知和风险**：固定站、移动装备、蓝黄橙红透明研判。
4. **决策与调度**：能力约束、距离/负荷评分、候选方案和人工确认。
5. **执行验证**：CARLA矿卡、BasicAgent、安全Waypoint多段导航。
6. **边坡案例**：风险升级、原车安全停车、任务释放、候选推荐、换车接管、工单闭环。
7. **数据闭环**：运行数据库、证据文件、地图资源库和后续学习数据。
8. **现状与下一步**：P5道路可达性、6～8车真实验证、多场景批量运行、训练策略对比。

## 10. 两分钟讲解稿

> 本项目面向露天矿在边坡风险、装备故障和道路异常条件下的安全高效调度需求，构建了一个CARLA数字矿山验证环境、智能调度后端和PyQt调度中心。底层使用CARLA 0.9.10加载自定义矿山地图和矿卡模型，利用BasicAgent完成车辆的油门、制动、转向和路线跟踪。后端将固定监测站和移动装备观测融合为风险输入，通过可解释的蓝黄橙红阈值模型输出风险等级、趋势和触发原因。
>
> 在调度层，系统首先根据车辆健康状态和能力进行硬约束筛选，再采用距离、当前任务负荷和有限历史经验偏好构成综合代价评分，选择最适合的装备。当边坡风险升级导致原车受影响时，系统会使原车进入安全状态，释放未完成任务，生成候选接管车辆和推荐理由，并在调度中心等待人工确认。确认后，新车辆通过CARLA继续执行原任务目标，执行事件再回传给工单、风险和运行状态，形成感知、研判、调度、执行、反馈的实时闭环。
>
> 为支持后续多车辆和多场景，项目还建设了独立地图资源库，已完成单车出生点、双车出生冲突和道路规划可达性验证。运行过程中的任务、风险、决策、工单和监测数据则写入运行数据库与证据文件。当前规则策略作为安全基线，后续将在不破坏安全约束的前提下，以这些数据开展风险模型、学习型调度和风险感知路径优化的对比验证。
